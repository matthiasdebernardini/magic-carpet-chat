# e2e-cua: the end-to-end suite on the cua box

One command from the Mac, one report at the end:

    scripts/e2e-cua/run.sh <run-id|path-to-binary|installed>

- `<run-id>`: a GitHub Actions run; `gh run download` fetches its `magic-carpet-chat-linux-x86_64` artifact.
- `<path>`: a Linux x86_64 binary or a `.tar.gz` holding one.
- `installed`: keep the e2e binary already in the `mc` container.

`run.sh` copies the binary into `mc` as `/usr/local/bin/magic-carpet-chat-e2e`, beside the demo's `magic-carpet-chat`, which it never touches. It syncs this folder to `~/mc/e2e/` on `magic-carpet-cua.exe.xyz`, runs `suite.py` there, and copies the run back to `/tmp/mc-e2e/<timestamp>/`. It exits nonzero if any scenario fails. The box never compiles and never needs a GitHub token. The suite takes over the desktop and relaunches `~/mc/run-app.sh` at the end.

Development flags (after the first argument): `--no-paid` skips P, R and Y, `--only A,G` runs a subset (Y runs only when named there), `--mock-jev` makes no TypeSafe calls, `--no-restore` leaves the desktop as the suite left it. `--reuse-wallets <run-id>` (Y only) seeds Y's two newcomers from that run's R store in `mc`'s trash (`/root/.trash/e2e-stores/<run-id>/R/accounts.json`, which must hold exactly two app-made Coinos accounts), copied with jq inside `mc`, instead of making two new Coinos accounts: Coinos refuses signups after a few from one network a day ("Too many accounts created from this network"). Their names come from their old kind-0, read from the app.

## What each scenario checks

Every scenario starts from a clean state: a fresh `MC_STORE_DIR`, the app relaunched with its own env, and an ffmpeg x11grab recording. A to H run against `fake_instance.py` (inside `mc` on 127.0.0.1:8787) and a `nak serve` relay on 127.0.0.1:10547, so nothing reaches the real instance. Two exceptions reach live services: trust reads of the fake-target scenarios go to the local relay, and R publishes two "E2E Newcomer …" kind-0 profiles (with a Lightning address) to the public relays, because the instance target leaves `MC_TRUST_RELAYS` unset. H and P talk to live coinos.io for the claimant's wallet balance. R makes two new Coinos wallets there. H needs that wallet to hold sats, or its sats-left check fails.

## Every scenario drives through the accessibility tree

The suite finds controls by their stable ids (`docs/a11y-ids.md`) in the app's AT-SPI tree, never by OCR, screen coordinates or colour. `atspi.py` runs inside `mc`; the driver kinds are `("press", id)` (the control's AT-SPI "click"), `("click_id", id)` (an xdotool click at the control's centre from its tree extents: to focus a text input, which has no action, or to click a step button drawn disabled, which has no click handler), `("wait_id", id)` and `("scroll_to", id)`. An id can be `~regex` with an exact `name`, e.g. a rail tab by account name. Exactly one node must match, and a control outside the window is refused: gpui presses by clicking the centre and has no scroll-into-view. `scroll_to` turns the mouse wheel over the control's column, three clicks at a time, and reads its extents from the tree after each turn until its centre is in the window (the Remove card at the foot of Identity & keys, step 3 of the Trust tab). A bounty is never selected by pressing its row, which can sit below the fold: `("select_bounty", list)` presses Down in the app's window one row at a time and reads `bounty-detail-title` after each, stopping at this run's list (at most one press per row plus one, never Enter). Each launch shortens the window so all of it is on the screen (screen height minus the client's top and the frame's bottom, from `_NET_FRAME_EXTENTS`).

Keys stay only where the key is what a scenario tests: Enter in a form's last field, Esc in A, `ctrl+a` before typing into a field, and `select_bounty`'s Down. Navigation is the sidebar's `nav-*` tabs, account switches the rail's `rail-account-<pubkey>` tabs (they go through the same `set_account` as super+]). xfce binds super+r to its Application Finder, so super+r never reaches the app; a claim card's latest state comes from selecting the bounty again.

Hard checks read node names: every node's AT-SPI name is its visible text. Buttons, tabs, headings and groups carry it as their label; a Label carries it as its value, which `src/a11y.rs` sets on Linux. A binary built before that change gives every Label an empty name, so the checks on Label wording (form errors and status lines, "Coinos wallet ready", "Auto-pay armed", the payment state, the recalc states) fail there. Jev still picks each step's candidate and judges its postcondition from the screenshot's OCR, so a press that reaches the wrong control fails the step; before any claim the published bounty's detail pane must show this run's list (`bounty-detail-title`), a 100-sat reward (`bounty-detail-reward`) and its cap (`bounty-detail-cap`: 100 sats for P, 200 for R and Y), and before each paying Enter the claim form's accessible name must read exactly "Claim an item on <list> · 100 sats per item". The submit step has no cancel candidate.

Pixels are read in one place, where the tree cannot say it: X's check that a search hit draws its picture and not its initials (`avatar_spread`). The avatar has no node; its region comes from the hit row's tree rect (`community-hit-<pubkey>`) and the window's place, not from OCR.

Setup: `mc` needs `python3-gi`, `gir1.2-atspi-2.0` and `x11-utils` (for `xwininfo`) from apt. Each scenario starts (or reuses) a session bus at `/tmp/e2e/a11y-bus` with its own `XDG_RUNTIME_DIR` (so the accessibility socket is not the desktop's), switches `org.a11y.Status IsEnabled` on, and launches the app with that `DBUS_SESSION_BUS_ADDRESS`. If the bus does not come up, or right after launch `xwininfo`, the app window or its first control (`rail-add-account`, or `setup-create` on a first launch) is missing, the scenario fails before it does anything (before any account, in R and Y). `atspi.py` only reads the app whose pid is `pidof -s magic-carpet-chat-e2e`, or the pid given with `--pid` (Y's two apps). To look at the tree by hand, with the e2e app running:

    docker exec mc sh -c 'DBUS_SESSION_BUS_ADDRESS=unix:path=/tmp/e2e/a11y-bus python3 /tmp/e2e/atspi.py dump'

`atspi.py selfcheck` is the helper's check: on an app launched with an empty `MC_STORE_DIR` and no `MC_NSECS` (the "Your Nostr account" card), it finds the choose card's ids, opens "Create a new account" and goes back. It never presses Create.

### Y: two apps on one desktop

Every action, AT-SPI read and screenshot in Y is pinned to one app: `atspi.py --pid` reads that process's tree, xdotool addresses its window id, "key" and "type" first make its window the active one and check that it is, and Jev's OCR reads that app's 1280x960 half of the screen, so the OCR boxes line up as with one app. xfwm's frame adds 5 px on each side, so each window is 1290 px wide: A's frame spans x 0-1290 and B's 1290-2580, on a 2580 px screen. At half width (640 px) the app is not usable: the header button and the detail pane fall outside the window, so Y widens the screen instead.

After the publish, A claims in App A; then App B is restarted (only its pid, on its own store), must show A's claim, and B claims; App A must show B's claim live. On the box nothing can make a running app refetch its bounty list: its refresh is super+r, and xfce binds super+r to its Application Finder. A launch reads the list (`Shell::new` sends FetchBounties), and claims then arrive live on a selected bounty. Keys and text for a pinned app go to its window id with `xdotool key/type --window`, after a check that the window is the active one. xdotool then delivers them as events addressed to that window (XSendEvent), not to whichever window has the focus; the app accepts them (tested on the fake).

Y runs fast steps: a step with one candidate runs without a Jev choose, reuses the previous after-look as its "before", and skips the screen-settling poll when its actions end in an id wait that found its control. Jev still judges every after-look (second look and the 0.6 threshold unchanged). Every scenario's report.json now carries per-step phase timings (ocr, jev_choose, act, settle, stable, jev_done) and per-scenario totals, printed at the end of each scenario.

## The float

P needs at least 200 sats in the instance's agent-wallet, R or Y at least 250 (two payouts plus fees), R and Y together 454, P, R and Y together 556 (Y runs only when `--only` names it); below that the suite stops before it starts and says so. Y spends about 204 like R and leaves the same kind of leftovers. P spends about 102 sats (100 payout plus fees), R about 204; a run with both P and R needs 352 and spends about 306. A run that stops between R's publish and B's payout leaves an open auto-pay bounty with up to 200 sats of cap on the instance; with the box's trust-gate bypass, any key that reaches the instance could claim a leftover bounty. Each R run also leaves about 100 sats in each of two throwaway Coinos wallets, whose logins end up in `/root/.trash` with the store. An e2e bounty closes after its payout, so a leftover one never pays again. To top up, on the box:

    ~/mc/fund.sh 500

and pay the invoice it prints (it expires in 10 minutes). If a payment fails, the suite reports it and does nothing else; see "Auto-pay operations" in `~/mc/README.md` for a manual reset.

## Output

The scenario stores (`/root/e2e-stores/<run>` in `mc`) hold copies of the nsecs; the suite moves them to `mc`'s root-only `/root/.trash/` at the end of each run.

`/tmp/mc-e2e/<timestamp>/`: `report.md`, `report.json` (scenario, result, evidence path, Jev picks and verdicts, hard checks, duration), `suite.out`, and per scenario `<ID>/<ID>.mp4`, `frames/` (PNG plus OCR text per observation), `app.log`, `fake-server.log`. Evidence shows at most the first 8 characters of an nsec.

## Add a scenario

1. Write `async def scenario_x(sc)` in `scenarios.py`: `sc.box.start_fake({...})` (modes are in `fake_instance.py`), `await start(sc, "X")` (launch, bus and preflight; stop when it returns None), then `await sc.step(Step(goal, [Cand(...)], done, cues=...))` for each UI action. Add `must_act=True` when the goal state is already on screen before the action.
2. Drive by id: `("press", id)`, `("click_id", id)` then `("type", text)` for a field, `("wait_id", id)` for the next state. Add hard checks with `sc.check_tree(...)` (tree reads), `sc.check(...)` or `sc.log_after(marker)`. A scenario with no hard check of its own (after the launch preflight's) fails. A control or text with no id in `docs/a11y-ids.md` needs one in the app first.
3. Register it in `SCENARIOS`. Candidates must never create a wallet, really remove an account, or publish outside the fake server (except P and R).
